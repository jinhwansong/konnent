## 1. 프로젝트 개요
- 서비스 한 줄 요약: 예약 → 실시간 세션 → 결제까지 흐름이 끊기지 않도록 한 화면에서 이어지는 1:1 멘토링 서비스
- 이 프로젝트는 개인 풀스택 프로젝트로, “프론트에서 기대하는 UX”를 끝까지 지키려면 백엔드/실시간까지 같이 맞춰야 한다고 판단해 함께 구현했습니다.
- 목표는 기능을 많이 넣는 것보다, 멘토링에 필요한 상태 변화(예약 확정/세션 시작/결제 결과)가 사용자에게 바로 체감되게 만드는 것이었습니다.

## 2. 문제 정의
- 멘토링은 “예약 폼 → 메신저 → 화상 툴 → 결제 링크”로 흩어져 있는 경우가 많아서, 화면을 옮길 때마다 집중이 끊긴다고 느꼈습니다.
- 승인/거절이나 세션 시작처럼 중요한 변경이 늦게 반영되면, 사용자는 계속 새로고침하거나 메시지를 확인해야 해서 불필요한 스트레스가 생깁니다.
- 프로필/리뷰로 신뢰를 확인하고, 바로 세션에 들어가서 대화하고, 결제까지 마치는 흐름이 한 화면에서 자연스럽게 이어지도록 만들고 싶었습니다.

## 3. 기술 스택
- **TypeScript**: 예약/결제처럼 실수 비용이 큰 화면에서 “데이터 형태가 틀리면 바로 깨진다”는 문제를 줄이기 위해 타입으로 계약을 고정했습니다.
- **Next.js**: 첫 진입은 빠르게 보이고(SSR), 이후 화면 전환은 앱처럼 매끄럽게(클라이언트 인터랙션) 만들기 위해 선택했습니다.
- **React Query + Zustand**: 서버 데이터(예약/세션/결제)는 캐시/동기화가 중요했고, UI 상태(모달/장치 설정)는 가볍게 분리하고 싶어서 역할을 나눴습니다.
- **Socket.IO + WebRTC**: “상태가 바뀌면 바로 보이는 UX”가 필요해서 실시간 채널을 두었고, 화상은 WebRTC 연결을 Socket 이벤트로 시그널링하도록 구성했습니다.
- **NextAuth + JWT(RS256)**: 인증은 흐름을 단순하게 유지하되, REST와 Socket에서 같은 기준으로 검증되게 맞추고, 프론트에서는 토큰을 헤더/인증 파라미터로만 사용하도록 정리했습니다.

## 4. 폴더 구조와 역할
- `frontend/src/app`: 화면(라우트)을 기준으로 책임을 끊었습니다. 인증/메인/멘토링/관리자 흐름을 나눠두니, 기능을 추가할 때 “어느 페이지에 영향을 주는지”가 먼저 보였습니다.
- `frontend/src/components`, `hooks`, `stores`: 실시간 이벤트가 섞이면 컴포넌트가 쉽게 비대해져서, UI/데이터 로직을 분리해 수정 범위를 줄였습니다.
- `backend/src`: 프론트의 흐름(예약→세션→결제)을 유지하려면 API와 실시간 이벤트가 같이 움직여야 해서, `auth`, `reservation`, `session`, `payment`, `realtime`을 도메인 단위로 정리했습니다.

## 5. 핵심 기능 설계
- 예약 슬롯 관리: “가능한 시간만 보여줘도” 실제 확정 타이밍이 엇갈리면 이중 예약이 생길 수 있어서, 승인/취소 이벤트를 받자마자 화면의 예약 상태를 바로 갱신하도록 구성했습니다.
- 실시간 세션(채팅/화상): 세션 중에 외부 툴로 이동하지 않게 하는 게 핵심이라, 채팅은 Socket으로, 화상은 WebRTC로 처리하고 시그널은 Socket 네임스페이스로 분리했습니다.
- 결제/정산: 결제는 실패 케이스가 UX를 망가뜨리기 쉬워서, 성공/실패가 나면 화면이 즉시 “다음 행동”을 안내하도록 흐름을 고정했습니다.
- 알림: 놓치면 곧바로 노쇼로 이어지는 이벤트(예약 확정/세션 시작)는 인앱 실시간 + 푸시/메일로 채널을 나눠 전달하도록 했습니다.
- 채팅 히스토리: 대화가 길어질수록 스크롤이 무거워지는 문제를 예상해서, 커서 기반 무한 스크롤과 파일 전송(메타데이터 중심)으로 데이터 흐름을 단순하게 유지했습니다.
- 성능/체감 개선: `next/image`, 동적 로딩, 라우트 단위 분리로 “첫 화면이 늦게 뜬다”는 체감을 줄이려고 했습니다.

## 6. 트러블슈팅 및 고민
- “승인했는데 화면이 그대로인” 문제: 서버에서 상태는 바뀌었는데 화면이 늦게 따라오면 사용자 입장에서는 실패처럼 느껴졌습니다. 그래서 이벤트 수신 시 캐시를 무효화하고, 필요한 화면은 즉시 업데이트하도록 바꿨습니다.
- “배포 후에만 Socket이 끊기는” 문제: 로컬에서는 잘 되는데 배포 환경에서는 간헐적으로 끊겨서 원인을 찾는 데 시간이 걸렸습니다. 프록시 업그레이드 헤더/타임아웃 설정을 정리하고 나서야 안정화됐습니다.
- “토큰을 어디에 두는 게 맞나” 고민: 편의성 때문에 클라이언트 저장소에 두고 싶었지만, 위험을 감수할 이유가 없다고 판단했습니다. 세션 기반 + 헤더 전달로 사용 범위를 줄였습니다.
- “첫 화면이 무거운” 체감: 에디터/화상처럼 무거운 기능이 초기 번들에 섞이면 진입 자체가 답답해졌습니다. 필요한 화면에서만 로드되도록 분리해 체감이 나아졌습니다.

## 7. 현재 자동화 현황
- 혼자 운영해도 부담이 덜하도록, 배포와 반복 작업을 최소화하려고 했습니다.
  - GitHub Actions로 백엔드 빌드/배포 흐름을 자동화하고, PM2 재시작으로 반영되게 구성했습니다.
  - 정산 같은 반복 작업은 스케줄러로 처리해 “수동으로 체크해야 하는 일”을 줄였습니다.
  - 알림은 이벤트 발생 시 자동 발송되게 해, 운영자가 개입하지 않아도 흐름이 이어지게 했습니다.

## 8. 개선 예정 사항
- 아직 부족하다고 느끼는 부분 위주로 정리했습니다.
  - 화상 세션 품질: 네트워크에 따라 품질이 흔들릴 때 자동 조정 흐름을 더 다듬고 싶습니다.
  - 결제 실패 UX: 실패 케이스별로 “왜 실패했는지/어떻게 복구하는지” 안내를 더 명확히 하고 싶습니다.
  - 상태 관리/초기 로딩: 실시간 화면에서 상태가 늘어날수록 복잡해져서, 더 단순한 구조로 정리해보고 싶습니다.

## 9. 사용 예시 (이미지)
- 메인/멘토 프로필: “신뢰 확인 → 예약”으로 이어지게 구성한 화면 (데모 링크 참고)
- 실시간 세션: 채팅/화상/알림이 한 화면에서 이어지는 세션 화면 (데모 링크 참고)
